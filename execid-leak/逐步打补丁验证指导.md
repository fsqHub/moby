# Docker v1.13.1 逐步打补丁并编译 RPM 包验证指导

## 目标

在 Docker v1.13.1 基础上逐步应用 ExecID 泄漏相关的 patches，每次应用后编译 RPM 包并验证问题是否解决，以精确定位修复拓展场景问题的最小补丁集。

---

## 前置准备

### 1. 系统要求

- **操作系统**: CentOS 7 / RHEL 7 或更高（推荐 CentOS 7.x，与 v1.13.1 发布时期匹配）
- **架构**: x86_64 (amd64)
- **磁盘空间**: 至少 20 GB 可用空间
- **内存**: 建议 8 GB 以上

### 2. 安装构建依赖

```bash
# 更新系统
sudo yum update -y

# 安装基础构建工具
sudo yum install -y \
    git \
    gcc \
    make \
    rpm-build \
    rpmdevtools \
    createrepo \
    device-mapper-devel \
    btrfs-progs-devel \
    libseccomp-devel \
    pkgconfig \
    systemd-devel \
    tar \
    wget

# 安装 Docker（用于构建环境）
sudo yum install -y yum-utils
sudo yum-config-manager --add-repo https://download.docker.com/linux/centos/docker-ce.repo
sudo yum install -y docker-ce docker-ce-cli containerd.io
sudo systemctl start docker
sudo systemctl enable docker

# 将当前用户加入 docker 组（需要重新登录生效）
sudo usermod -aG docker $USER
```

### 3. 安装 Go 1.7.5

Docker v1.13.1 需要 Go 1.7.x 版本：

```bash
# 下载 Go 1.7.5
cd /tmp
wget https://golang.org/dl/go1.7.5.linux-amd64.tar.gz

# 解压并安装
sudo tar -C /usr/local -xzf go1.7.5.linux-amd64.tar.gz

# 配置环境变量
cat >> ~/.bashrc <<'EOF'
export GOROOT=/usr/local/go
export GOPATH=$HOME/go
export PATH=$GOROOT/bin:$GOPATH/bin:$PATH
EOF

source ~/.bashrc

# 验证安装
go version  # 应输出: go version go1.7.5 linux/amd64
```

## Docker RPM 编译完整流程

### 方法一：使用 Docker 容器构建（推荐）

v1.13.1 使用容器化构建流程，这是最稳定的方式。

#### Step 1: 构建 Docker 引擎二进制

```bash
cd ~/docker-patch-test/moby-1.13.1

# 设置版本信息
export VERSION=1.13.1
export DOCKER_GITCOMMIT=$(git rev-parse --short HEAD)

# 构建 Docker 开发环境镜像
make build

# 编译动态链接的二进制（RPM 需要）
make dynbinary

# 检查生成的二进制
ls -lh bundles/$(cat VERSION)/dynbinary-daemon/
```

**预期输出**:
```
dockerd-1.13.1
dockerd-1.13.1.md5
dockerd-1.13.1.sha256
```

#### Step 2: 构建 RPM 包

```bash
# 方式 1: 使用 Makefile 目标（推荐）
make rpm

# 方式 2: 手动调用构建脚本
# export VERSION=1.13.1
# hack/make.sh dynbinary build-rpm
```

**构建过程说明**:

1. 脚本会检测系统架构（amd64）
2. 为每个支持的发行版（CentOS 7, Fedora 24/25 等）构建 RPM
3. 使用 `dockercore/builder-rpm` 系列镜像作为构建环境
4. 打包 docker-engine 和 docker-engine-selinux RPM

**构建时间**: 首次构建约 10-20 分钟（需要下载基础镜像）

#### Step 3: 查找生成的 RPM

```bash
# RPM 包位置
find bundles/$(cat VERSION)/ -name "*.rpm"

# 典型输出示例:
# bundles/1.13.1/build-rpm/centos-7/RPMS/x86_64/docker-engine-1.13.1-1.el7.centos.x86_64.rpm
# bundles/1.13.1/build-rpm/centos-7/RPMS/noarch/docker-engine-selinux-1.13.1-1.el7.centos.noarch.rpm
```

#### Step 4: 验证 RPM 包

```bash
# 查看 RPM 包信息
rpm -qip bundles/$(cat VERSION)/build-rpm/centos-7/RPMS/x86_64/docker-engine-*.rpm

# 查看包含的文件
rpm -qlp bundles/$(cat VERSION)/build-rpm/centos-7/RPMS/x86_64/docker-engine-*.rpm | head -20
```

### 方法二：本地直接构建（适用于调试）

如果容器化构建遇到问题，可以尝试本地构建：

#### Step 1: 配置 RPM 构建环境

```bash
# 创建 RPM 构建目录结构
rpmdev-setuptree

# 目录结构:
# ~/rpmbuild/
# ├── BUILD/
# ├── RPMS/
# ├── SOURCES/
# ├── SPECS/
# └── SRPMS/
```

#### Step 2: 准备源码包

```bash
cd ~/docker-patch-test/moby-1.13.1

# 设置版本
export VERSION=1.13.1
export DOCKER_GITCOMMIT=$(git rev-parse --short HEAD)

# 构建二进制
AUTO_GOPATH=1 ./hack/make.sh dynbinary

# 打包源码
cd ..
tar --exclude=.git -czf ~/rpmbuild/SOURCES/docker-engine.tar.gz moby-1.13.1/
```

#### Step 3: 复制 spec 文件并修改

```bash
# 复制 spec 文件
cp ~/docker-patch-test/moby-1.13.1/hack/make/.build-rpm/docker-engine.spec ~/rpmbuild/SPECS/

# 编辑 spec 文件，确保版本号正确
sed -i "s/%{_version}/$VERSION/g" ~/rpmbuild/SPECS/docker-engine.spec
sed -i "s/%{_gitcommit}/$DOCKER_GITCOMMIT/g" ~/rpmbuild/SPECS/docker-engine.spec
```

#### Step 4: 构建 RPM

```bash
cd ~/rpmbuild/SPECS

# 构建二进制 RPM
rpmbuild -bb \
    --define "_gitcommit $DOCKER_GITCOMMIT" \
    --define "_release 1" \
    --define "_version $VERSION" \
    --define "_origversion $VERSION" \
    docker-engine.spec

# 或构建源码+二进制 RPM
rpmbuild -ba \
    --define "_gitcommit $DOCKER_GITCOMMIT" \
    --define "_release 1" \
    --define "_version $VERSION" \
    --define "_origversion $VERSION" \
    docker-engine.spec
```

#### Step 5: 查看生成的 RPM

```bash
ls -lh ~/rpmbuild/RPMS/x86_64/
```

4. 记录问题是否解决

#### 第 4 组：Context Cancel（2022-08）- **核心修复**

这个 patch 是解决拓展场景的关键之一，但依赖较新的 containerd 接口。

```bash
cd ~/docker-patch-test/moby-1.13.1
git checkout -b patch-group-4

# 尝试应用
git am ~/docker-patch-test/patches/0001-daemon-kill-exec-process-on-ctx-cancel.patch
```

**如果无法直接应用，核心移植点**:

1. 在 `daemon/exec.go` 的 `ContainerExecStart` 中添加 goroutine 监听 `ctx.Done()`
2. 当 context 取消时，调用 `libcontainerd` kill exec process

```go
// 示例代码片段（需要根据 v1.13.1 API 调整）
go func() {
    select {
    case <-ctx.Done():
        if err := daemon.containerd.SignalProcess(containerID, execID, int(syscall.SIGKILL)); err != nil {
            logrus.Errorf("failed to kill exec process: %v", err)
        }
    case <-attachErr:
        // exec 正常完成
    }
}()
```

```bash
cd ~/docker-patch-test/moby-1.13.1
```

3. 手动移植 epoll 监听代码

### Patch 应用的实际困难

#### 问题 1: API 不兼容

**现象**: patch 涉及的文件路径、函数签名在 v1.13.1 中不存在或不同。

**解决方案**:
1. **理解 patch 的核心意图**，而非机械应用
2. 查看 v1.13.1 的对应代码位置
3. **手动移植核心逻辑**
4. 编写简单的 integration test 验证移植效果

#### 问题 2: 依赖的 containerd 版本不匹配

**现象**: v1.13.1 使用 containerd 0.2.x，但某些 patches 依赖 1.x 或更高版本的 API。

**解决方案**:
1. 检查 `vendor/` 目录中 containerd 的版本
2. 如果 API 不兼容，评估是否可以用旧 API 实现相同功能
3. 考虑升级 containerd（但可能引入其他兼容性问题）

#### 问题 3: 累积冲突过多

**解决方案**:
1. **放弃逐个应用所有 patches**
2. **只移植最关键的 2-3 个修复**：
   - Context cancel kill exec（第 4 组）
   - Client disconnect 检测（第 5 组）
   - Stream I/O timeout（第 3 组）
3. 其他改进作为次要优化

```bash
cat > reproduce-issue.sh <<'EOF'
#!/bin/bash

echo "=== 启动 54 个容器 ==="

echo "=== 开始并发 exec 测试 ==="
for i in {1..54}; do

    )

echo "=== 检查 dockerd goroutine 数量 ==="

EOF
```

## 常见问题排查

### 问题 1: 编译失败 - "cannot find package"

**原因**: Go 依赖包未正确 vendor 或 GOPATH 未设置。

**解决**:
```bash
# v1.13.1 使用 vendor 机制
cd ~/docker-patch-test/moby-1.13.1
ls vendor/  # 确认依赖包存在

# 确保 Go 版本正确
go version  # 应该是 1.7.5

# 清理并重新构建
make clean
make build
```

### 问题 2: RPM 构建失败 - "docker daemon not running"

**原因**: 构建过程需要 Docker daemon。

**解决**:
```bash
sudo systemctl start docker
sudo systemctl status docker

# 确保当前用户在 docker 组
groups | grep docker
# 如果没有，需要重新登录或使用 sudo
```

### 问题 3: Patch 应用失败 - "patch does not apply"

**原因**: 代码结构差异较大。

**解决**:
```bash
# 查看 patch 内容
cat patch-file.patch

# 尝试宽松模式
git apply --reject --whitespace=fix patch-file.patch

# 手动合并 .rej 文件
find . -name "*.rej"

# 或完全手动移植
vim affected-file.go
# 参考 patch 内容手动修改
git add affected-file.go
git commit -m "Manual port: [patch description]"
```

### 问题 4: 测试时 Docker 无法启动

**原因**: 编译的二进制有问题或依赖缺失。

**解决**:
```bash
# 查看 systemd 日志
sudo journalctl -xeu docker.service

# 手动运行 dockerd 查看详细错误
sudo /usr/bin/dockerd -D

# 检查 SELinux（如果启用）
sudo setenforce 0
sudo systemctl restart docker
```

基于之前的分析，预期：

- **Group 1（3cc0d6bb04）**: 修复 `invalidcommand` 场景，但不解决拓展场景

**建议**: 如果目标是定位修复，优先使用**方案 A（跨版本对比）**，效率更高；如果需要在 v1.13.1 上提供修复包，再考虑手动移植核心逻辑。
